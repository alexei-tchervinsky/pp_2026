# pp_2026
SPbPU Demo for Praktikum (merge conflicts resolutions)

# Настольная компьютерная игра "Кто первый" :-) для освоения совместной работы над проектом с разрешением конфликтов слияния (merge conflicts)

## Введение
В курсе ТП мы делаем лабораторные, используя форки и, что **важно** - работая каждый в собственных каталогах. Таким образом, мы никак не затрагиваем работу друг друга. 
В реальных проектах, во-первых, форки обычно не используются (форк означает некий новый вариант проекта, который можно развивать независимо) и, во-вторых, достаточно часто несколько разработчиков независимо от друга изменяют один или несколько общих файлов. При этом команда `push` ветки может приводить к **конфликту слияния** (merge conflicts). При конфликте git вписывает в файл **маркеры** (специальные текстовые строки) и, если, например, файл - это код C++, то эти маркеры приведут к тому, что код даже не скомпилируется. В таких ситуациях ответственность разработчика - это разрешить конфликт слияния, то есть отредактировать файл (локально или на github), удалив маркеры и добившись компиляции и сборки кода. В общем случае, разрешение конфликтов слияния может быть нетривиальной задачей, если между разработчиками слабая координация и тот, кто пытается удалить маркеры и получить некий общий код, не полностью понимает замысел другого разработчика и, в худшем случае, действует по своему усмотрению. Маркеры будут удалены, код даже может компилироваться, но результат этого слитого кода может не соответствовать ожидаемому. 

Мы рассмотрим простейший случай разрешения конфликтов слияния, пытаясь на каждом шаге получать корректный работающий код.

## Алгоритм разрешения конфликтов в общем виде
### Первый раунд
- Имеем **один репозиторий** в начальном состоянии. В репозитории на ветке `main` находится файл `main.cpp` в начальном состоянии. Каждый разработчик клонирует это репозиторий на свой компьютер.

### Второй раунд
- Каждый разработчик в своей локальной копии создает ветку от `main` и редактирует `main.cpp`
- После редактирования `git add`, `git commit`, **но не делает** `git push`
- **Один из разработчиков**, которого назначает ведущий (преподаватель), делает `git push`
- И создает Pull Request для своей ветки
- В этом PR никаких конфликтов **нет**
- Ведущий мержит ветку разработчика в `main`

###  Третий раунд
- Следующий разработчик, которого назначает ведущий, **делает** `git push` своей ветки, на которой находится **его редакция** файла `main.cpp`
- Этот разработчик создаёт Pull Request
- Поскольку его редакция `main.cpp` была из ветки `main`, какой она была **до второго раунда**, то в PR он увидит на своей странице сообщение `Merge Conflicts`
- Конфликт возникает потому, что ветка `main`, которую разработчик склонировал в первом раунде, была **обновлена** первым разработчиком во втором раунде
- Таким образом, по-сути, есть две ветки `main` - начальное клонирование и текущее состояние в репозитории на GitHub
- В своём PR можно посмотреть файл и увидеть в нем **маркры конфликта слияния**, примерно такие:
```
Group  5130904/50003
tsuremichev.ga
chervinskij_ap
chervinskij_ap 2
chervinskij_ap 4
tsuremichev.ga 2
chervinskij_ap 3
<<<<<<< HEAD
chervinskij_ap 7
=======
chervinskij_ap 6
>>>>>>> main
```
- Маркер `<<<<<<< HEAD` до маркера `=======` определяет изменения **текущей** ветки разработчика
- Маркер  `=======` до маркера `>>>>>>> main` определяет изменения, которые были внесены разработчиком во втором раунде
- Очевидно, что указанные маркеры, которые являются просто строками, не позволят скомпилировать код ни на каком языке программирования

### Четвёртый раунд
Файл с конфликтами должен быть отредактирован, то есть маркеры **дожны быть удалены** с тем, чтобы в файле остались изменения первого разработчика и изменения текущего разрботчика, и при этом файл **должен компилироваться**
Удалить маркеры можно и на веб странице PR, однако при этом невозможно скомпилировать файл
Поэтому разрешение конфликтов слияния (то есть удаление маркеров) нужно произвести **локально**
Для этого:
- в локальном репозитории сделать
  - `git switch main`
  - `git pull` - скачается текущая версия `main.cpp`, которая **не содержит маркеров** - эта версия второго раунда 
  - `git checkout -` перейти на свою ветку
  - `git merge main` - применить изменения ветки `main` к своей ветке (жаргонно: _подтянуть main_)
  - и вот на этом шаге `merge main` git выдаст сообщение о конфликтах слияния, в файле будут `маркеры`, которые видели на странице PR
  - нужно отредактировать `main.cpp`, удалив маркеры так, чтобы в файле остались изменения предыдущего разработчики и добавились изменения текущего разработчика
  - **проверить локально**, что файл компилируется и даёт ожидаемый результат
  - в случае успеха
    - `git add`
    - `git commit -m "resolved merge conflicts"`
    - `git push`
  - теперь на странице PR исчезнет сообщение о конфликте и появится `Ready to merge`

### Пятый раунд
Ведущий мержит PR без конфликтов, и теперь на ветке `main` в репозитории корректный файл с общими изменениями

Возвращаемся к раунду 3, то есть ведущий назначает следующего разработчика, который следует инструкциям раундов 3 и 4

### Шестой раунд (заключительный)
Теперь на ветке `main` репозитория находится файл `main.cpp` со **всеми изменениями**
Каждый разработчик локально
- `git switch main`
- `git pull`
- каждый имеет идентичный файл `main.cpp`
- собрать и запустить файл
- получаем идентичный результат суммарных изменений

## Правила для нашего репозитория:
### Именование своих веток:
это идентификатор `в корпоративной почте`, например:
- `chervinskij_ap`
- `tsuremichev.ga`
  
Использование других идентификаторов, например, `Vitaly` или `Валюшка` **недопустимо**

### Добавление корпоративного email в массив `email`:
-  `chervinskij_ap@spbstu.ru`
-  `tsuremichev.ga@edu.spbstu.ru`

Использование других email, личных **недопустимо**   

### Сообщение в коммите раундов 2 и 3 аналогично, то есть
- `git commit -m "chervinskij_ap"`
- `git commit -m "tsuremichev.ga"`
### Сообщение в коммите раунда 4 (разрешение конфликта)
- `git commit -m "chervinskij_ap resolve conflicts"`
- `git commit -m "tsuremichev.ga resolve conflicts"`
